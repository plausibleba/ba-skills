# Reviewer 3 — LLM Pipeline Architect Response

**Filed:** 2026-05-08
**Reviewer remit:** Whether the LLM pipeline can reliably produce well-formed CAPSICUM-shaped output — externalised Outcomes with `stateOf`/`triggers`, AgentCharter shape, and SHACL-driven repair loops — from real discovery transcripts.
**Files read on disk:** `spike/graph-runtime/REPORT.md`, `src/shape/capsicum.ttl`, `src/fixtures/claims-settlement.ttl`, `src/20-validate.ts`; `packages/frontend/src/domain/pipeline/prompts/pass-b-scaffold-formalisation.ts`, `scaffold-formaliser.ts`, `scaffold-gates.ts`, `prompts/pass-c-friction-analysis.ts`, `prompts/pass-c-ppit-enrichment.ts`, `prompts/pass-a2-capability-mapping.ts`, `discovery-ir.ts`, `pipeline-orchestrator.ts`; `packages/frontend/src/types.ts` (ScaffoldActivity, ScaffoldOutcome, LifecycleState, RecordClass).

---

## 1. Position

**Endorse-with-amendments, contingent on a pipeline-side spike before lock.** The runtime decision and ontology shape stand on their own legs; the metamodel commitment to externalised Outcome is right *as a target*, but the current pipeline does not produce the inputs that target requires. Pass B today emits a linear `nextActivityId` chain with `preOutcomeId`/`postOutcomeId` strings and `lifecycleStates[]` *internalised on InfoObjects*; it does not emit `Outcome.stateOf → BusinessObject` triples, does not emit `Outcome.triggers → Stage`, does not produce non-linear progression, has no notion of a `RecordClass` link (the type exists in `types.ts` but no Pass populates `primaryRecordClassId` or `lifecycleStateId`), and has no AgentCharter generator at all. The spike fixture was hand-built; nothing in the pipeline today emits its shape. Locking the metamodel without first proving the pipeline can produce one well-formed externalised Outcome graph from one real transcript is the rough equivalent of locking a wire format before the encoder exists.

## 2. Single biggest hidden risk

**The `stateOf` predicate has no source signal in the pipeline today.** It is hidden because the spike sidesteps it — the fixture *asserts* `Outcome_ClaimReceived cap:stateOf claims:Claim` because the spike author knew there was a `Claim` business object. The pipeline doesn't know that. Pass A2 produces a four-level capability hierarchy where each L4 has a `businessObject` field, but Pass B does not propagate that into Outcomes — it produces Outcomes whose only content is `{ name, elementType }` (see `pass-b-scaffold-formalisation.ts` lines 245). There is no concept of a **RecordClass registry being populated by the LLM at all** — `recordClasses` appears in `types.ts` and in Pass D context, but no upstream pass writes it. To populate `Outcome.stateOf` reliably, Pass B (or a new pass) needs to (a) materialise a RecordClass per VS, (b) link each Outcome to it, and (c) reconcile when a stage transitions *multiple* business objects (the Claim becomes Validated, but a Subrogation Case is also opened). None of that machinery exists. What would expose it: re-run Pass B against the Water Filtration Co. transcript and ask the LLM to emit `outcomes[*].stateOf` — measure how often the value is plausible vs. hallucinated vs. omitted.

## 3. Externalised Outcome under prompt (A) — **partially plausible**

Re-prompting Pass B to emit `stateOf` and `triggers` is mechanically tractable for the *structural* part — the prompt already has fierce determinism rules and produces an n+1 outcomes-per-VS pattern (`pass-b-scaffold-formalisation.ts` line 222 *"Create one Outcome per stage boundary"*). Adding `triggers` is essentially mechanical: `Outcome[i].triggers = Stage[i+1]` is a deterministic re-encoding of today's `nextActivityId` chain. So the *first* pass at "externalised Outcome under prompt" will succeed by emitting linear progression in different syntax — passing Reviewer-2's structural assertions while delivering none of the value the externalisation was meant to unlock (state-based VS navigation, non-linear branching, multi-stream feedback loops).

The *real* failure modes I'd predict:

1. **`stateOf` hallucination.** With no RecordClass registry, the LLM will invent business object names per Outcome, and the same business object will surface under different labels across stages of the same VS ("Claim", "Insurance Claim", "Submitted Claim"). The dual-field bug C1+C2 catches will recur as a `cap:stateOf <claim:Claim>` vs `cap:stateOf <claim:InsuranceClaim>` divergence — no SHACL rule the spike has currently catches that, because the cardinality is right and the IRI is well-formed.
2. **`triggers` collapsing to linear.** The LLM has been instructed for thirty-six sessions to produce a single linear chain. Asking it to produce non-linear `triggers` graphs without redesigning the upstream Discovery IR (which itself records stages as a list, not a state machine) will yield linear chains with `triggers` as a re-spelling of `nextActivityId`. The branching that motivates externalisation never appears.
3. **Outcomes that are not states.** The current prompt produces Outcome names like *"Lead Qualified"* that are state-shaped, but Pass B has no mechanism to reject non-state outcomes ("Customer Engagement Improved" is a *change*, not a state); the SHACL constraints in the spike enforce *reference* (every Outcome must trigger something) but not *semantics* (every Outcome must be a stative noun phrase referencing the named business object). This is a class of error the LLM will reliably produce that no constraint catches.

## 4. AgentCharter generation (B)

This is genuinely a **multi-pass orchestration with mandatory human-in-the-loop interleave**, not a single-pass generation, and not Pass C territory. The PRD's five enrichments → eight scoring dimensions → classification → AgentCharter is an entire downstream pipeline. The right place for it is a new **Pass F (Agentic Enablement)** that runs *post-scaffold seal*, takes a single Capability as input, and walks: (1) PPIT enrichment (the only piece that exists today, Pass C); (2) Decision Inventory enrichment — needs a new prompt that grounds in actual decision points the user confirms, since LLMs invent decisions liberally; (3) Exception Profile — likewise grounded; (4) Inter-Capability Dependency — a graph derivation, not an LLM pass at all (compute it from `enabledByCapability` adjacency in the graph); (5) Regulatory Constraint — almost certainly a retrieval-augmented step, not pure inference.

The AES eight-dimension score and classification *can* be a single LLM call given the five enrichments as context — that's a structured-output rubric application, which LLMs do reliably. The AgentCharter content (decision surface specification) cannot. The PRD says decision surface design is part of the AgentCharter; the LLM cannot produce a useful decision surface without grounding in actual UI examples and authority deontics, neither of which exist in any current pipeline output. Without those, the LLM will produce a plausible-looking but useless surface description ("Agent presents claim summary, recommends adjudication, requests user approval") that survives validation and fails in deployment. **Recommendation:** AgentCharter generation is Layer-4 commercial-plugin scope. Layer-1 OSS pipeline should stop at "Capability has AES score and classification" and leave the deontic norm tuples and decision surface specification to the proprietary plugin that runs against real customer UI/policy assets.

## 5. Migration regression risk (C)

Specific risks I can name:

1. **`getCapabilityIds()` is a tell.** `types.ts:377` already wraps the v4/v5 split. The pipeline doesn't trust its own field names. Migration to externalised Outcome requires a *third* alias to mediate — `outcome.stateOf` will join `requiresCapabilityIds`/`enabledByCapabilityIds` as a co-existing-field pattern. If you don't fix the pattern now, you'll be writing `getOutcomeStateOf(o)` against three field shapes by v0.7.
2. **Pass C friction analysis assumes the linear-chain shape.** `pass-c-friction-analysis.ts:30-54` builds a scaffold skeleton that emits `preOutcomeId`/`postOutcomeId`/`nextActivityId` and *only* those — no stateOf, no triggers. After the metamodel shift the skeleton needs reshaping; otherwise heatmap observations are computed against a representation that no longer carries the structural signal (binding-constraint `downstreamDependency` becomes trivially scorable from `triggers`, but only if the skeleton exposes it).
3. **Gate 1 hand-rolled walker (`scaffold-gates.ts:46-110`) is structurally married to `nextActivityId`.** The cycle/reachability check walks the linear chain. Under externalised Outcome, "reachability" means *transitive closure over `triggers` from all initial Outcomes*. This is not a small rewrite; the gate has to become a graph walker over the JSON-LD or (better) be re-expressed as SPARQL ASK over the loaded graph. Same code path can't service both shapes.
4. **`primaryRecordClassId` is wired into types but never written.** This is the obvious anchor for `stateOf`. The migration can repurpose it: if Pass B emits `Activity.primaryRecordClassId` and the loader derives `Outcome.stateOf = activity.primaryRecordClassId` from the postOutcome, you reduce the LLM's surface area.
5. **The lean-vs-rich Pass B split (Session 28).** Pass B was deliberately stripped to FSM + IO lifecycle to fit in token budgets. Asking it to also emit RecordClass + Outcome.stateOf + non-linear triggers will breach that envelope; it will need either splitting again or a deterministic post-processor that walks the lean output and assembles the RDF shape.

**Transition pattern recommendation.** Hard-cutover for the *internal* representation (Zustand → graph store) and **dual-shape loader** for bundles. The loader should accept either v5 scaffold JSON or v0 CAPSICUM JSON-LD and normalise to the graph in memory. Hard-cutover internally because you're solo and three readers across two shapes is what the codebase is already drowning in (`getCapabilityIds`, `vs.zone ?? vs.layoutZone`). Dual-shape externally because D-095 requires it and customers have v5 bundles.

## 6. SHACL in the pipeline (D)

Bounded-repair against SHACL works *if and only if* the SHACL violation reports come back as structured JSON, not as a `?focus IRI` row that the spike's SPARQL-ASK currently produces. Looking at `scaffold-formaliser.ts:108`, the repair loop literally pastes `gate1.errors` (string array) into the prompt as a bullet list — the LLM has been getting human-readable error strings, and that's what the LLM knows how to repair. SHACL `ValidationReport` graphs (`sh:focusNode`, `sh:resultPath`, `sh:value`, `sh:resultMessage`) carry richer structure but need to be *serialised back to natural language* before the LLM can do anything with them. If you switch to `rdf-validate-shacl` cold, the repair-loop prompt has to be rewritten to either include the message templates literally or render the report graph to text.

The deeper failure mode: **SHACL violations on properties the LLM doesn't control.** Pass B's repair loop works because every Gate-1 error is on a field the prompt explicitly told the LLM to emit. A SHACL constraint of the form "every Outcome must have `stateOf` pointing at a RecordClass that exists in the graph" can fail because (a) the LLM omitted `stateOf`, (b) it pointed at a RecordClass IRI that doesn't exist, or (c) the RecordClass *itself* failed an upstream constraint and was dropped. Cases (b) and (c) are not repairable by re-prompting Pass B alone — the failure is cross-pass, and the bounded-repair pattern doesn't compose across passes today. **Recommendation:** keep SPARQL-ASK as the in-pipeline gate (it's exactly the bug-detection surface the v4/v5 dual-field bug needs); layer full SHACL only at the bundle-publish boundary, where validation can fail loudly and the user fixes content rather than the LLM repairing structure.

## 7. Pipeline-output shape (E)

**Intermediate shape with deterministic transformer.** The LLM should keep emitting JSON-shaped scaffold (or a thin variant of it that adds `stateOf`/`triggers`/`primaryRecordClassId`), and a deterministic post-processor should map that to JSON-LD with the published `@context`. Three reasons: (1) the pipeline has spent thirty-six sessions tuning the JSON output and the determinism/repair pattern is mature; throwing that away to teach the LLM JSON-LD ceremony is pure regression risk; (2) `@context` references break differently than missing fields — a mistyped `@type` is a class of error the validator can't auto-repair the way it can auto-repair a missing `requiresCapabilityIds`; (3) the JSON-LD encoder is a few hundred lines of TypeScript that you can unit-test against the spike's shape, vs. a recurring per-call prompt-engineering cost that you cannot. The spike's bundle (`claims-settlement.bundle.jsonld`) is precisely the artefact a deterministic encoder should produce — keep the LLM out of that loop.

Turtle-as-intermediate is tempting (more forgiving than JSON-LD) but worse on net: the LLM produces less-reliable Turtle than JSON because it has fewer training examples of TTL emission as a target, and Turtle errors are harder to auto-repair than JSON ones (`repairTruncatedJSON` in `scaffold-formaliser.ts:34` has no Turtle equivalent).

## 8. One concrete thing to spike before locking

**Run Pass B against the Water Filtration Co. transcript with a modified prompt that emits `stateOf`, `triggers`, `primaryRecordClassId`, and a `recordClasses` registry — then validate the JSON output against an expanded SHACL that asserts (a) every Outcome.stateOf points at an existing RecordClass, (b) the `triggers` chain reaches every non-initial stage, (c) RecordClass labels are unique within VS scope.** Three runs at temperature 0, log how many constraint violations fire per run, and how many are auto-repairable in one bounded loop. Success bar: ≥ two of three runs pass all constraints with at most one repair iteration. Failure bar: hallucinated business objects, linear `triggers` chains, or unrecoverable validation in the repair loop. This isolates the *pipeline* question (can the LLM produce the metamodel) from the runtime question (can oxigraph store it) and the ontology question (is the shape coherent). About a day of work.

## 9. Decision recommendation

**Endorse the runtime, endorse the metamodel target, but require a pipeline-rework spike before locking the externalised-Outcome commitment in DEC-NNN.** The four-criteria spike proves *the runtime can host* the metamodel — it does not prove *the pipeline can produce* it. Locking now means committing to a metamodel where the canonical predicates (`stateOf`, `triggers`) have no upstream source signal, which will manifest in production as Outcomes with hallucinated business object IRIs, linear-chains-in-triples-clothing, and an AgentCharter generator that cannot be built without leaving the OSS layer. Re-frame the lock as: **runtime + ontology shape locked at v0.6; pipeline migration phased with explicit Phase-1 = `stateOf` only, Phase-2 = `triggers` graph, Phase-3 = AgentCharter (commercial layer).** The bundle portability invariant (D-095) survives this phasing — the `@context` is the same; later versions add predicates rather than reshape them.

The SPAR's anti-pattern check stands: this isn't a relitigation of "graph is canonical" or "CAPSICUM is the metamodel". It's the specific narrower point that a metamodel commitment the LLM pipeline can't reliably populate is — to use the briefing's own language — no commitment at all, just a deferred one.
