# Op Model Workbench — Design Document

_Created: 2026-03-23 — Session 26_

## Vision

The Op Model Workbench is VCC's **engine room** — the place where Business Architects go to structurally improve an operating model. It sits alongside the analyst's project-centric views (Network, Stage, Friction) but serves a different role: enterprise alignment, governance consistency, and structural integrity.

The analyst generates and explores. The architect refines and aligns.

Today's Architectural Review Export (Session 25) is a one-click export. The Workbench replaces that with a full multi-step refinement workflow: orient → review catalogs → get AI-assisted proposals → reconcile → regenerate. The export becomes just the final step.

---

## Mental Model

**The engine room metaphor.** When you enter the Workbench, you leave the polished views behind. You're looking at the plumbing — the catalogs, registries, and cross-references that make the model structurally sound. The aesthetic shifts: darker palette, more structural, less presentational. You're not reading a map; you're checking the wiring.

**Catalog-first design.** Every element in the scaffold belongs to a catalog (capabilities, concepts, value streams, roles, etc.). The Workbench presents these as editable collections — spreadsheet grids for bulk operations, card views for understanding context. The architect works catalog by catalog, then validates cross-references.

**Agent-assisted, architect-decided.** Refinement agents propose changes based on natural language feedback. The architect always has the final say — every proposal is a diff they accept, reject, or modify. No silent mutations.

## Entry Points

### 1. From Project List (dedicated use case)

"Op Model Workbench" appears as a use case type alongside the existing BA use case. A Business Architect creates one by importing an existing project's model, or claims a project that was generated by an analyst.

### 2. From Network View (contextual entry)

An "Enter Workbench" button on the Network View toolbar. Same model, different lens. The architect drills down from the strategic overview into the structural layer.

Both doors lead to the same room. The Workbench always operates on a project's scaffold data.

## Stepped Workflow

### Step 1 — Orientation

**Purpose:** Explain what the Workbench does and let the architect scope their review.

**Content:**
- Brief explanation of the refinement process and its quality impact
- The five refinement types (from the existing design doc) with their quality contributions:

| Refinement Type | Quality Contribution | Impact |
|----------------|---------------------|--------|
| Capability Map | Foundational | Highest single-edit impact — everything references capabilities |
| Concept Model | Ontological | Fixes what the org manages — ripples through grounding |
| Value Streams & Stages | Delivery narrative | Fixes how value flows — ripples through mappings |
| Stage-to-Cap Mapping | Cross-reference accuracy | Most common AI error — wrong caps in wrong stages |
| Full Model Review | Comprehensive | Architect reviewed everything — cross-validation pass |

**Interaction:** Architect selects which catalogs they want to review. This scopes Steps 2–3 to only the relevant catalogs. "Full Review" selects all.

**UI:** Clean, instructional panel. Not a wizard — more like a briefing before entering the engine room.

**Grid features:**
- Sorting by any column (click header)
- **Column drag-to-reorder** — drag column headers to rearrange layout (TanStack column ordering + @dnd-kit/core)
- **Column pinning** — freeze Name column (or any column) on the left while scrolling horizontally. Pin/unpin via right-click header menu
- Filtering by text search + column-specific filters
- Multi-select rows → batch delete, batch tag, batch reclassify
- Add row (bottom of grid or inline)
- Undo/redo stack (Ctrl+Z / Ctrl+Shift+Z)
- Dirty indicator per cell (amber dot) and per catalog (badge count)
- TanStack Table as the grid engine (~15KB, handles virtual scrolling, column ordering, and column pinning natively)

#### Card View (contextual understanding)

For each catalog item, a card showing:
- The item's fields (same as grid, but laid out vertically)
- **Relationship panel:** what references this item and what it references (bidirectional). E.g., a capability card shows which activities require it, which business object it governs, and its parent/child capabilities.
- **Provenance note:** where this item came from (generated by Pass B, user-created, refined in workbench)

Cards are read-and-edit — click any field to edit inline. But the primary edit surface is the grid; cards are for understanding relationships before deciding what to change.

**Toggle:** Toolbar button switches grid ↔ cards. Grid is default. State persists per catalog within the session.

### Step 3 — Refinement Agent

**Purpose:** AI-assisted editing via natural language feedback.

**Interaction model:** Chat panel (right sidebar, ~350px wide, collapsible). The architect types natural language feedback and the agent proposes structured diffs.

**Example conversation:**

> **Architect:** "Customer Onboarding and Client Setup should be merged — they're the same capability in our org."
>
> **Agent:** Here's the proposed change:
>
> | Action | Element | Before | After |
> |--------|---------|--------|-------|
> | Merge | cap_customer_onboarding + cap_client_setup | Two separate L4 capabilities | Single "Customer Onboarding" capability |
> | Update | act_initial_engagement | requiresCapabilityIds: [..., cap_client_setup] | requiresCapabilityIds: [..., cap_customer_onboarding] |
> | Delete | cap_client_setup | Exists | Removed |
>
> **[Accept] [Modify] [Reject]**

**Agent architecture:**
- New LLM call site (8th in the app), streaming through existing Edge Runtime proxy
- New prompt file: `domain/pipeline/prompts/refinement-agent.ts`
- Input: current catalog state (the specific catalog being reviewed) + conversation history + architect's latest message
- Output: structured diff operations (JSON array of add/modify/delete/merge/split/move actions)
- Diff schema enforces referential integrity — merge operations automatically update all cross-references
- Context window: the agent sees only the catalog(s) currently in scope, not the entire scaffold. This keeps token usage reasonable and focused.

**Diff operations:**

```typescript
type DiffOperation =
  | { action: 'add'; catalog: CatalogType; element: Partial<ScaffoldElement> }
  | { action: 'modify'; catalog: CatalogType; elementId: string; field: string; before: unknown; after: unknown }
  | { action: 'delete'; catalog: CatalogType; elementId: string; cascadeUpdates: CascadeUpdate[] }
  | { action: 'merge'; catalog: CatalogType; sourceIds: string[]; targetId: string; mergedElement: Partial<ScaffoldElement>; cascadeUpdates: CascadeUpdate[] }
  | { action: 'split'; catalog: CatalogType; sourceId: string; newElements: Partial<ScaffoldElement>[]; cascadeUpdates: CascadeUpdate[] }
  | { action: 'move'; catalog: CatalogType; elementId: string; newParentId: string }

type CascadeUpdate = {
  catalog: CatalogType;
  elementId: string;
  field: string;
  before: unknown;
  after: unknown;
}
```

**Agent capabilities by catalog:**
- **Capabilities:** merge, split, reparent, rename to org terminology, suggest missing L4 children, flag orphans
- **Concepts:** reclassify (Party→Record), merge duplicates, suggest missing properties, flag ungrounded objects
- **Value Streams:** resequence stages, suggest missing stages, merge thin stages, flag disconnected flows
- **Mappings:** reassign capabilities to correct stages, flag stages with no capabilities, flag capabilities not used in any stage
- **Roles:** merge duplicate roles (common AI error: "Analyst" vs "Risk Analyst" vs "Senior Analyst"), suggest RACI-like separation

**Conversation is stateful** within the session (full message history maintained) but not persisted. It's a working conversation, not a record.

### Step 4 — Reconciliation

**Purpose:** Cross-catalog validation after edits are complete.

**Validation checks:**

| Check | Severity | Auto-fixable |
|-------|----------|-------------|
| Orphaned capability (not referenced by any activity) | Warning | Suggest: assign to most likely stage |
| Stage with no capabilities | Error | Suggest: assign from VS-level capabilityIds |
| Business object not grounding any capability | Warning | Suggest: link to relevant L4 cap |
| Role referenced but not in roles registry | Error | Auto-fix: add to registry |
| Outcome referenced but not in outcomes registry | Error | Auto-fix: add to registry |
| Capability references non-existent parent | Error | Suggest: reassign or promote to L1 |
| Broken activity chain (nextActivityId points to missing activity) | Error | Auto-fix: relink chain |
| Duplicate names within same catalog | Warning | Suggest: merge or disambiguate |
| Metric targeting non-existent element | Error | Suggest: retarget or remove |

**Presentation:** Checklist view. Each issue shows what's wrong, which elements are affected, and a suggested fix. Architect can accept fix, dismiss, or handle manually (jump to catalog).

**This is essentially Gate 2 (referential integrity) from the scaffold pipeline, but interactive and with repair suggestions rather than just pass/fail.**

### Step 5 — Regenerate

**Purpose:** Feed the refined model back through the generation pipeline.

**What happens:**
1. Architect clicks "Regenerate Model"
2. VCC sends the refined scaffold to the Edge Runtime proxy with a regeneration prompt
3. The prompt specifies exactly what was refined (from Step 1 scope) and what must be preserved vs rebuilt (from the existing refinement type prompt strategies)
4. The pipeline rebuilds dependent artefacts around the architect's corrections
5. The regenerated model loads directly back into the project — no file download, no manual reload
6. Before/after summary shows what changed in the regeneration

**Regeneration is selective and single-pass.** When multiple catalogs are refined, regeneration runs one combined pass (not sequential passes that might undo each other). The architect's edits across all refined catalogs are preserved verbatim.

**Regeneration algorithm order** — the combined pass applies refinements in a defined dependency order, shown to the architect before they confirm:

```
1. Capabilities (foundation — everything references these)
     ↓
2. Concepts / Business Objects (grounded against capabilities)
     ↓
3. Value Streams & Stages (delivery structure references caps + concepts)
     ↓
4. Stage-to-Capability Mappings (cross-references between 1 and 3)
     ↓
5. PPIT / Roles / Metrics (derived from all of the above)
```

This order is displayed in the Step 5 UI as a visual pipeline so the architect understands how the logic flows. The prompt preserves everything the architect explicitly edited and rebuilds the rest top-down through the dependency chain.

**Future: configurable algorithm order.** In a later phase, the architect could opt to reverse the derivation direction — e.g., "derive Value Streams from Capabilities" (top-down, default) vs "derive Capabilities from Value Streams" (bottom-up, for process-first organisations). This changes the prompt strategy but uses the same regeneration infrastructure.

**Architecture:**
- New API endpoint: `/api/regenerate.ts` (Edge Runtime, streaming)
- Uses the existing `callLLM()` infrastructure from `llm-client.ts`
- Prompt constructed from refinement type templates (already defined in `REFINEMENT-LOOP-DESIGN.md`)
- Response parsed and merged back into the project's scaffold store
- Conflict detection: if regeneration would overwrite something the architect explicitly edited, flag it for review

**Fallback:** The existing export-and-reimport flow (Session 25) remains available as a manual alternative. The "↻ Refine" button in the header still works for users who prefer the Cowork round-trip.

## Visual Design — The Engine Room

The Workbench uses a distinct visual language to signal "you're in a different mode":

| Element | Main VCC | Workbench |
|---------|----------|-----------|
| Background | White/light grey | Slate-900 / dark charcoal |
| Accent colour | Blue/purple | Amber-500 / warm industrial |
| Typography | System sans-serif | Monospace hints on IDs and field names |
| Grid lines | Subtle | Visible — structural grid |
| Icons | Lucide outline | Lucide solid — heavier weight |
| Header | "VCC" branding | "Op Model Workbench" with gear icon |
| Navigation | Tab bar | Stepped progress (Steps 1–5) |

The transition should feel like moving from a dashboard into a control room. Not jarring — the same design system — but clearly a different mode of operation.

### Steam Puff (regeneration celebration)

When a regeneration completes (Step 5), a brief CSS animation plays: a puff of steam rising from the "Regenerate" button area. 2–3 translucent white wisps that rise and fade over ~1.5 seconds. Implemented as CSS keyframe animation on absolutely-positioned pseudo-elements — no canvas, no library, just a few divs with opacity and transform transitions.

Small touch, but it gives the architect a satisfying moment after what might be a long review session. Can be toggled off in settings if users find it distracting.

## Catalog-Agnostic Architecture

The grid, card, agent, and diff infrastructure are designed to be **catalog-agnostic**. Each catalog is defined by a configuration object:

```typescript
type CatalogConfig = {
  id: CatalogType;                        // 'capabilities' | 'concepts' | 'valueStreams' | ...
  label: string;                          // Display name
  icon: string;                           // Lucide icon name
  scaffoldKey: string;                    // Key in scaffold.elements
  columns: ColumnDef[];                   // TanStack Table column definitions
  cardLayout: CardFieldDef[];             // Fields to show on card view
  agentSystemPrompt: string;              // Catalog-specific agent instructions
  validationRules: ValidationRule[];      // Reconciliation checks
  refinementType: RefinementType;         // Maps to prompt strategy
}
```

**Why this matters:** When scenario analysis arrives, it slots in as a new catalog configuration — "scenario constraints" with its own columns, card layout, agent prompt, and validation rules. No new infrastructure needed.

## State Management

### Workbench Store (Zustand)

```typescript
type WorkbenchStore = {
  // Session state
  isActive: boolean;
  currentStep: 1 | 2 | 3 | 4 | 5;
  selectedCatalogs: CatalogType[];

  // Edit state (per catalog)
  catalogEdits: Record<CatalogType, DiffOperation[]>;
  undoStack: Record<CatalogType, DiffOperation[][]>;
  redoStack: Record<CatalogType, DiffOperation[][]>;

  // Agent state
  agentMessages: Record<CatalogType, ChatMessage[]>;
  pendingDiffs: DiffOperation[];        // Proposed but not yet accepted

  // Reconciliation state
  validationIssues: ValidationIssue[];

  // Derived
  dirtyCount: number;                   // Total uncommitted edits
  workingScaffold: ScaffoldData;        // Original scaffold + applied edits
}
```

The `workingScaffold` is a derived view: the original scaffold with all accepted edits applied. This is what the grid renders and what gets sent to the regeneration pipeline.

## Implementation Phases

### Phase 1 — Catalog Grids (foundation)

Build the grid infrastructure and basic editing:
- Workbench route + navigation (enter from Network View)
- Orientation step with catalog selection
- TanStack Table integration with catalog configs
- Capabilities grid (most complex — tree-grouped, drag-to-reparent)
- Value Streams grid
- Activities grid
- Grid ↔ Card toggle
- Workbench Zustand store with edit tracking and undo/redo
- Engine room visual theme

**Deliverable:** Architect can enter the Workbench, browse catalogs in grid view, make manual edits, and see dirty counts. No agent, no regeneration yet.

### Phase 2 — Refinement Agent

Add the AI-assisted editing layer:
- Chat sidebar component
- Refinement agent prompt (`refinement-agent.ts`)
- Diff schema and diff rendering (before/after tables)
- Accept/reject/modify flow
- Cascade update logic (merge a capability → update all referencing activities)
- Remaining catalog grids (concepts, roles, metrics)

**Deliverable:** Architect can chat with the agent, get proposed diffs, and accept them into the grid.

### Phase 3 — Reconciliation + Regeneration

Close the loop:
- Reconciliation validation engine (Gate 2 interactive)
- Fix suggestion + auto-fix flow
- `/api/regenerate.ts` endpoint
- Regeneration prompt construction from refinement scope
- Before/after summary view
- Return-to-Network-View flow with updated model

**Deliverable:** Full end-to-end refinement workflow. Architect enters, reviews, refines with agent help, validates, regenerates, and returns to the strategic view with an improved model.

### Phase 4 — Scenario Analysis (future)

Extend the catalog-agnostic architecture:
- New catalog type: scenario constraints
- Scope-of-work selector (which VS/stages are in scope for optimisation)
- Constraint editor (budget, timeline, resource limits)
- Scenario comparison (run multiple constraint sets, compare outputs)

## Resolved Decisions

1. **Workbench persistence** — Phase 1: ephemeral (lost on page refresh). Phase 2: agent conversation history optionally saved or summarised as session logs to Supabase. This gives architects a record of their refinement reasoning, useful for audit trails and handoff to other team members.

2. **Concurrent editing** — **Commit model.** The Workbench operates on a working copy of the scaffold. Network/Stage views do not update live. The architect explicitly clicks "Apply Changes" to write back to the canvas store. This prevents half-finished edits from confusing the analyst views.

3. **Tier gating** — Individual tier ($50/mo) or above. Gated action: `enter_workbench`. Free/starter users see the Workbench entry point but get an upsell modal. Feature preview GIFs (screen recordings of the Workbench in action) shown in the upsell modal and in the app for unlicensed features, so users can see what they're missing.

4. **Agent token budget** — Catalog context is scoped to the catalog currently being reviewed, not the entire scaffold. For very large models, paginate or summarise. Additionally: regeneration is a metered action. Users get a base allocation of regeneration credits per billing cycle, with the option to purchase additional credits. This caps cost exposure while letting power users do more.

5. **Regeneration scope** — **Single combined pass** with a merged prompt. Defined dependency order (Capabilities → Concepts → VS/Stages → Mappings → PPIT/Roles/Metrics) shown to the architect before confirmation. Future phase: configurable derivation direction (top-down vs bottom-up).

## Open Questions

1. **Feature preview GIFs** — how many and where? Candidates: Workbench grid editing, agent diff proposal, reconciliation checklist, steam puff regeneration. Need to decide whether these are pre-recorded or auto-generated from test data.

2. **Session log format** — when agent conversations are saved (Phase 2), what's the schema? Raw message history, or a summarised "refinement journal" with decisions and rationale? The journal format is more useful for audit trails but requires an LLM summarisation step.

3. **Configurable algorithm order** — how to present this to the user without overwhelming them? Could be an "Advanced" toggle in Step 5 that reveals the dependency chain with drag-to-reorder. Or a set of named presets ("Capability-first", "Process-first", "Object-first").
